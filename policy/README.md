# Policy-as-Code

This directory holds the OPA/Conftest rules that gate every deployment in this
repo. They are evaluated by [`.github/workflows/policy-check.yml`](../.github/workflows/policy-check.yml),
which is called as a job from `deploy.yml` and runs **before** the Helm deploy
step. If the policy verdict is `block`, the job fails and the deploy job
(which `needs: policy-check`) never runs — the gate is enforced by GitHub
Actions' own dependency graph, not by convention.

## Why policy-as-code instead of a manual checklist

A checklist in a wiki page degrades the moment someone is in a hurry. Encoding
the same rules as Rego means: the rule text and the enforcement are the same
artifact, every decision is machine-readable (see below), and a change to the
rule is a reviewable pull request against this directory instead of a Slack
message asking someone to "remember to check."

## Rules

### `require-signed-image.rego` — POL-SIG-01

Blocks the deploy if the target image's cosign keyless signature cannot be
verified against the expected GitHub Actions OIDC identity. This is the
supply-chain integrity gate — an image that wasn't built and signed by this
repo's own `build.yml` (or whose signature can't be verified for any reason)
never reaches the cluster.

### `max-critical-cves.rego` — POL-7734

Blocks the deploy if the image's SBOM-derived vulnerability scan (via
[Grype](https://github.com/anchore/grype)) reports more than **3** Critical
severity CVEs. The threshold lives in the rule itself, not in a separate
config file, so the policy and its enforcement can never drift apart.

Both rules are `package main`, so Conftest evaluates them together as one
policy set when run against `policy/rules`.

## Input contract

`policy-check.yml` assembles a single JSON document per evaluation and feeds
it to `conftest test` — the rules above are written against this shape:

```json
{
  "image": "<registry>/<repo>:<tag>",
  "signature": { "verified": true },
  "cves": { "critical": 0, "high": 2 }
}
```

- `signature.verified` comes from `cosign verify` against the image, using
  the same GitHub OIDC identity that signed it in `build.yml`.
- `cves.critical` / `cves.high` come from running `grype` against the SBOM
  that was generated by Syft and attached to the image in `build.yml`,
  retrieved here with `cosign download sbom`.

## Output: the `PolicyDecision` record

Every run writes a structured `policy-decision.json`, uploaded as a workflow
artifact. Its shape matches the `PolicyDecision` node described in
[`graph/schema.md`](../graph/schema.md) exactly on purpose — the knowledge
graph ingests this JSON directly (`graph/ingest-policy-decision.mjs`), so
this is the single source of truth for what a "policy decision" is across
this whole project. Don't rename fields here without updating that schema.

```json
{
  "id": "pd-<run_id>-<run_attempt>",
  "deployment_id": "<blue_version>-<run_id>",
  "verdict": "pass",
  "evaluated_at": "2026-08-22T00:00:00Z",
  "rule_fired": [],
  "reason": "All policy checks passed: signature verified and critical CVE count within threshold.",
  "cves": { "critical": 0, "high": 2 },
  "image": "<registry>/<repo>:<tag>",
  "signature": { "verified": true },
  "approver": null
}
```

`rule_fired` is a list of rule slugs (`"max-critical-cves"`, `"require-signed-image"`)
extracted from whichever `deny` messages fired; it's empty when the verdict is
`pass`. `approver` is always `null` in Phase 1 — there is no manual override
path yet, which is deliberate: the point of this gate is that it can't be
talked around. A future approver/override flow is a graph-schema field
already reserved for it, not a promise this phase implements.

## Running it locally

```bash
# from the repo root, with conftest and a conftest-input.json in hand
conftest test conftest-input.json --policy policy/rules
```

## Scope note

This is a two-rule demo policy set proving the pattern (signed + within CVE
threshold), not a compliance framework. Adding a rule is: write a `.rego`
file in this directory with a `deny[msg]` rule, reference its rule id in the
message so `policy-check.yml`'s `rule_fired` extraction can recognize it, and
add a matching field to the input JSON if the rule needs new data.
